## Overview

The ML Platform uses a multi-layered security monitoring approach to detect, alert, and respond to security findings across the AWS infrastructure. This document provides step-by-step procedures for handling security incidents detected by our automated monitoring systems.

## Security Monitoring Stack

### Components

1. **AWS Security Hub**
   - Centralized security findings aggregator
   - Runs continuous compliance checks against:
     - CIS AWS Foundations Benchmark v1.4.0
     - AWS Foundational Security Best Practices v1.0.0
   - Consolidates findings from GuardDuty, Inspector, and other AWS services

2. **AWS GuardDuty**
   - Threat detection service for:
     - Unusual API calls
     - Potentially compromised EC2 instances
     - Reconnaissance activities
     - Kubernetes audit log analysis (EKS-specific)
     - S3 data access anomalies
     - Malware detection on EBS volumes

3. **AWS Inspector**
   - Automated vulnerability scanning for:
     - EC2 instances (operating system vulnerabilities)
     - ECR container images (package vulnerabilities)
     - Network exposure assessments

4. **EventBridge + SNS**
   - Real-time alerting for HIGH and CRITICAL findings
   - Email notifications to designated security contacts

## Severity Levels

### AWS Security Hub Severity Scale

| Severity | Score Range | Response Time | Description |
|----------|-------------|---------------|-------------|
| **CRITICAL** | 90-100 | Immediate (< 15 min) | Imminent threat requiring immediate action |
| **HIGH** | 70-89 | Urgent (< 4 hours) | Significant security risk requiring prompt attention |
| **MEDIUM** | 40-69 | Standard (< 24 hours) | Moderate risk requiring planned remediation |
| **LOW** | 1-39 | Routine (< 7 days) | Low risk, address during regular maintenance |
| **INFORMATIONAL** | 0 | As needed | Informational only, no action required |

### GuardDuty Severity Scale

| Severity | Score Range | Equivalent |
|----------|-------------|------------|
| **HIGH** | 7.0-8.9 | Security Hub: HIGH |
| **MEDIUM** | 4.0-6.9 | Security Hub: MEDIUM |
| **LOW** | 0.1-3.9 | Security Hub: LOW |

## Incident Response Phases

### 1. Detection & Alert

**Automated:**
- Security finding generated by Security Hub/GuardDuty/Inspector
- EventBridge rule matches HIGH/CRITICAL severity
- SNS sends email alert to security contacts

**What You'll Receive:**
```text
Subject: 🚨 Security Alert: CRITICAL Severity Finding

Title: [Finding Title]
Description: [Finding Description]
Resource: [Affected AWS Resource ARN/ID]
Region: us-west-2
Compliance Status: FAILED
Action: Review finding in AWS Security Hub console
```

### 2. Triage & Assessment

**Immediate Actions (< 15 minutes):**

1. **Acknowledge the alert** - Reply to the email or log the incident

2. **Access Security Hub Console:**
   ```bash
   # Get console URL from Terraform outputs
   cd terraform/environments/dev
   terraform output security_hub_console_url

   # Or directly:
   # https://us-west-2.console.aws.amazon.com/securityhub/home?region=us-west-2#/summary
   ```

3. **Review the finding details:**
   - Title and description
   - Affected resource(s)
   - Compliance status
   - Remediation recommendations
   - Related findings

4. **Assess impact:**
   - Is this a true positive or false positive?
   - What data/systems are at risk?
   - Is there evidence of active exploitation?
   - What is the blast radius?

5. **Determine severity and priority:**
   - Validate the assigned severity
   - Consider business context
   - Check for indicators of compromise (IOC)

### 3. Containment

**Immediate Containment (if exploitation detected):**

**For Compromised EC2/EKS Nodes:**
```bash
# Option 1: Isolate the instance (revoke security group rules)
aws ec2 modify-instance-attribute \
  --instance-id <INSTANCE_ID> \
  --groups <RESTRICTED_SG_ID>

# Option 2: Stop the instance (preserves forensics)
aws ec2 stop-instances --instance-ids <INSTANCE_ID>

# Option 3: Terminate and replace (for auto-scaled nodes)
kubectl cordon <NODE_NAME>  # Prevent new pods
kubectl drain <NODE_NAME>   # Evict existing pods
# Auto Scaling will launch replacement node
```

**For Compromised IAM Credentials:**
```bash
# Disable access keys
aws iam update-access-key \
  --access-key-id <ACCESS_KEY_ID> \
  --status Inactive \
  --user-name <USER_NAME>

# Attach deny-all policy (immediate effect)
aws iam put-user-policy \
  --user-name <USER_NAME> \
  --policy-name DenyAll \
  --policy-document '{"Version":"2012-10-17","Statement":[{"Effect":"Deny","Action":"*","Resource":"*"}]}'
```

**For Exposed S3 Buckets:**
```bash
# Block public access immediately
aws s3api put-public-access-block \
  --bucket <BUCKET_NAME> \
  --public-access-block-configuration \
    BlockPublicAcls=true,IgnorePublicAcls=true,BlockPublicPolicy=true,RestrictPublicBuckets=true
```

### 4. Eradication

**Remove the threat:**

1. **Patch vulnerabilities:**
   - Update vulnerable packages/AMIs
   - Apply security patches
   - Update container images in ECR

2. **Remove malicious artifacts:**
   - Delete backdoors, malware, unauthorized resources
   - Rotate compromised credentials
   - Revoke unauthorized access

3. **Fix misconfigurations:**
   - Update Terraform configurations
   - Apply security best practices
   - Enable required security controls

### 5. Recovery

**Restore normal operations:**

1. **Deploy fixes:**
   ```bash
   # Update Terraform configurations
   cd terraform/environments/dev
   terraform plan
   terraform apply

   # Update Kubernetes resources
   kubectl apply -f k8s/
   ```

2. **Verify remediation:**
   - Re-scan with Inspector
   - Check Security Hub compliance status
   - Test affected services

3. **Monitor for recurrence:**
   - Watch CloudWatch logs
   - Monitor GuardDuty findings
   - Check Security Hub dashboard

### 6. Lessons Learned

**Post-incident review (within 48 hours):**

1. Document the incident:
   - Timeline of events
   - Root cause analysis
   - Actions taken
   - Effectiveness of response

2. Update procedures:
   - Improve detection rules
   - Enhance response playbooks
   - Update Terraform configurations

3. Implement preventive measures:
   - Add automated remediation
   - Strengthen security controls
   - Update training materials

## Response Procedures by Finding Type

### GuardDuty Findings

#### 1. UnauthorizedAccess:EC2/MaliciousIPCaller

**Description:** EC2 instance is communicating with a known malicious IP

**Response:**
```bash
# 1. Immediately isolate the instance
aws ec2 modify-instance-attribute \
  --instance-id <INSTANCE_ID> \
  --groups sg-xxxxxxxxx  # Use restricted security group

# 2. Create forensic snapshot
aws ec2 create-snapshot \
  --volume-id <VOLUME_ID> \
  --description "Forensic snapshot - GuardDuty finding $(date +%Y%m%d)"

# 3. Review CloudTrail logs for API activity
aws cloudtrail lookup-events \
  --lookup-attributes AttributeKey=ResourceName,AttributeValue=<INSTANCE_ID> \
  --max-results 50

# 4. Terminate and replace
kubectl drain <NODE_NAME> --ignore-daemonsets --delete-emptydir-data
aws ec2 terminate-instances --instance-ids <INSTANCE_ID>
```

#### 2. CryptoCurrency:EC2/BitcoinTool

**Description:** EC2 instance running cryptocurrency mining software

**Response:**
```bash
# 1. Stop the instance immediately
aws ec2 stop-instances --instance-ids <INSTANCE_ID>

# 2. Check for unauthorized access
aws cloudtrail lookup-events \
  --lookup-attributes AttributeKey=ResourceName,AttributeValue=<INSTANCE_ID>

# 3. Review IAM access
aws iam list-attached-user-policies --user-name <USER_NAME>
aws iam list-access-keys --user-name <USER_NAME>

# 4. Terminate and launch fresh instance
# Ensure proper IAM permissions and security groups
```

#### 3. Recon:EC2/PortProbeUnprotectedPort

**Description:** Port scanning activity detected on EC2 instance

**Response:**
```bash
# 1. Review security group rules
aws ec2 describe-security-groups --group-ids <SG_ID>

# 2. Restrict unnecessary ports
# Update terraform/environments/dev/main.tf
# Remove overly permissive ingress rules

# 3. Enable VPC Flow Logs (if not already enabled)
aws ec2 create-flow-logs \
  --resource-type VPC \
  --resource-ids <VPC_ID> \
  --traffic-type ALL \
  --log-destination-type cloud-watch-logs \
  --log-group-name /aws/vpc/flowlogs

# 4. Monitor for follow-up attacks
```

### Security Hub Findings

#### 1. IAM.1 - Root account access key should not exist

**Description:** AWS root account has active access keys

**Response:**
```bash
# 1. List root account access keys
aws iam get-account-summary | grep "AccountAccessKeysPresent"

# 2. Delete root access keys immediately
aws iam delete-access-key --access-key-id <ROOT_ACCESS_KEY_ID>

# 3. Enable MFA for root account
# (Must be done via AWS Console)

# 4. Set up AWS Organizations and SCPs to prevent root usage
```

#### 2. EC2.2 - VPC default security group should not allow inbound/outbound traffic

**Description:** Default security group has open rules

**Response:**
```bash
# 1. Identify default security group
aws ec2 describe-security-groups \
  --filters "Name=group-name,Values=default" \
  --query "SecurityGroups[*].[GroupId,VpcId]"

# 2. Remove all ingress rules
aws ec2 revoke-security-group-ingress \
  --group-id <DEFAULT_SG_ID> \
  --ip-permissions <EXISTING_RULES>

# 3. Remove all egress rules
aws ec2 revoke-security-group-egress \
  --group-id <DEFAULT_SG_ID> \
  --ip-permissions <EXISTING_RULES>

# 4. Verify no resources are using default SG
aws ec2 describe-instances \
  --filters "Name=instance.group-id,Values=<DEFAULT_SG_ID>"
```

#### 3. S3.1 - S3 Block Public Access setting should be enabled

**Description:** S3 bucket allows public access

**Response:**
```bash
# 1. Check current public access settings
aws s3api get-public-access-block --bucket <BUCKET_NAME>

# 2. Enable block public access
aws s3api put-public-access-block \
  --bucket <BUCKET_NAME> \
  --public-access-block-configuration \
    BlockPublicAcls=true,IgnorePublicAcls=true,BlockPublicPolicy=true,RestrictPublicBuckets=true

# 3. Review bucket policy for public access
aws s3api get-bucket-policy --bucket <BUCKET_NAME>

# 4. Remove public access from bucket ACL
aws s3api put-bucket-acl --bucket <BUCKET_NAME> --acl private
```

### Inspector Findings

#### 1. CVE-xxxx-xxxxx - Package vulnerability

**Description:** Package vulnerability detected in EC2/ECR

**Response:**
```bash
# For EC2 instances:
# 1. Update the vulnerable package
ssh ec2-user@<INSTANCE_IP>
sudo yum update <PACKAGE_NAME>  # For Amazon Linux 2
sudo apt update && sudo apt upgrade <PACKAGE_NAME>  # For Ubuntu

# For ECR container images:
# 1. Update Dockerfile
# 2. Rebuild and push image
docker build -t ml-platform-api:v1.0.1 .
docker tag ml-platform-api:v1.0.1 <ECR_URL>:v1.0.1
docker push <ECR_URL>:v1.0.1

# 3. Update Kubernetes deployment
kubectl set image deployment/ml-platform-api \
  ml-platform-api=<ECR_URL>:v1.0.1

# 4. Verify fix with Inspector rescan
```

#### 2. Network Exposure - Port accessible from internet

**Description:** Instance has port exposed to 0.0.0.0/0

**Response:**
```bash
# 1. Review security group rules
aws ec2 describe-security-groups --group-ids <SG_ID>

# 2. Restrict to specific IP ranges
aws ec2 revoke-security-group-ingress \
  --group-id <SG_ID> \
  --ip-permissions IpProtocol=tcp,FromPort=22,ToPort=22,IpRanges='[{CidrIp=0.0.0.0/0}]'

aws ec2 authorize-security-group-ingress \
  --group-id <SG_ID> \
  --ip-permissions IpProtocol=tcp,FromPort=22,ToPort=22,IpRanges='[{CidrIp=203.0.113.0/24,Description="Office IP"}]'

# 3. Use Systems Manager Session Manager instead of SSH
# (Already configured in terraform/environments/dev/main.tf)
```

## Common Security Findings

### Top 10 Most Common Findings

1. **IAM password policy not configured** → Enable in AWS Console or via Terraform
2. **Root account MFA not enabled** → Enable via AWS Console
3. **CloudTrail not enabled** → Enable via Terraform
4. **S3 bucket public access** → Block public access
5. **Security group allows 0.0.0.0/0** → Restrict to specific IPs
6. **Unencrypted EBS volumes** → Enable encryption by default
7. **IAM access keys not rotated** → Rotate every 90 days
8. **VPC flow logs not enabled** → Enable via Terraform
9. **RDS instance publicly accessible** → Disable public access
10. **Unused security groups** → Remove unused resources

## Escalation Procedures

### When to Escalate

Escalate to senior security personnel if:

- **Active exploitation detected** (e.g., data exfiltration, lateral movement)
- **Compliance violation with legal implications** (e.g., GDPR, HIPAA)
- **Widespread impact** (affects multiple AWS accounts or critical systems)
- **Unable to contain** within response time SLA
- **Ransomware or destructive malware** detected
- **Root cause unclear** after initial investigation

### Escalation Contacts

1. **Technical Escalation:** Platform Engineering Lead
2. **Management Escalation:** Engineering Manager
3. **Legal/Compliance:** Legal Department (for compliance violations)
4. **AWS Support:** Open support case for account compromise

### Metrics to Track

- **Mean Time to Detect (MTTD):** Time from event to detection
- **Mean Time to Acknowledge (MTTA):** Time from detection to acknowledgment
- **Mean Time to Contain (MTTC):** Time from detection to containment
- **Mean Time to Remediate (MTTR):** Time from detection to full remediation
